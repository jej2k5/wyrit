# Phase 13 handoff

Open **Monitoring** in the loopback console. To view an agent host’s runs, start the console with the same configured ledger path as that host. The health strip describes the live console supervisor’s own connections. The server history shows recorded events from all supervisors sharing that path and identifies each supervisor.

- The feed shows completed runs in newest-first order. Each collapsed row shows the completion time, outcome, short capability sequence, duration, short run ID, and a preview of the first retained source line. Expand a row for the full ID, source, recorded reason or first denied call, original call order, and ledger link. Pause freezes new feed entries and resume catches up from the same cursor. A downstream check is suggested for UNKNOWN.
- Capability rates use named call attempts in the selected window. p50 and p95 use nearest rank over recorded durations. The health strip counts runs completed in the last hour. It flags limit hits and UNKNOWN actions, and compares failed and denied actions, failed runs, and runs with denied writes with the preceding 23 hours. Without baseline records for a comparison, any matching event is surfaced.
- Server history, reconnects, calls lost to connection drops, limit hits and write-policy denials use the selected window. Write denials and drops require an explicit audit reason. Older ledger rows still contribute to outcome rates and can show the single limit recorded at the time.
- Source links return the exact JSON record with its file name, inode and line number. The initial feed shows the latest 50 records available in the current file. Once an inode is observed, the tail keeps its read position and follows late appends across rename rotation. Open rotation segments and scanned records stay in memory for the console session. Rotation performed entirely between polls can leave an intermediate file unobserved.
- Configured-host execution retains generated JavaScript for seven days by default. Arguments and available results start off and have separate opt-in settings. **Capture settings** controls both policies per server and namespace. If a run attempts calls to multiple known servers, source capture uses the shortest retention and stops if any of those servers disables it. Runs with no attributable server use the default. Shortening retention applies to existing source, and turning it off purges affected runs immediately. Earlier ledger entries may have no retained source or recorded failure reason.
- Source and payloads live in a private SQLite sidecar. Known resolved credentials and credential-shaped strings suppress capture, and the ledger records only a withholding marker. Monitoring displays “source withheld: looked like a credential” for those runs. Expired data becomes unavailable at its deadline and a running supervisor sweeps once a second, including paths seen before a live reload. Existing expired rows are swept when a supervisor next opens the same ledger path. SQLite secure deletion applies to retained rows. Filesystem snapshots and backups have their own retention.
- The console writes bare TOML keys where possible and uses inline header references. Header rows show whether their environment variables are set and preserve the config validator and atomic edit flow.

The trusted host still owns session access, the run authorization check and transport dispatch. Monitoring records and captures remain in the host process and are unavailable through the generated runtime. The public action outcome codes and replay behavior are unchanged.
