# Phase 15: Lean discovery and clear outcomes

The phase 14 benchmark (2026-11-23, Claude Code on `claude-opus-5-5`, 3 repetitions) showed Wyrit losing on small tasks: 34 to 65% more list-price cost and about twice the wall time of direct tool calls, at equal correctness. Most of the gap is one extra model turn: the agent calls `search` to learn the capability IDs, then `execute`, and every turn re-reads the whole context. On a 30-call fan-out Wyrit already won (half the cost). This phase removes the extra turn for small catalogs and fixes the one real correctness miss.

**1. Catalog in the `execute` description.** Render a compact capability catalog into the `execute` tool's description so an agent can write code on its first turn without calling `search`: for each exposed capability its ID, one-line description, read or write class, and a compact argument signature derived from the input schema (names, types, required marks; no full JSON Schema). Bound it: at most 8 KB and 60 capabilities. Above either bound, list the namespaces with their capability counts and tell the agent to use `search`. `search` stays available and unchanged. When the catalog changes (phase 9 refresh, reload, policy change) the description is regenerated and the MCP server emits `notifications/tools/list_changed` so clients refetch it. The description also documents, in two or three lines, how results and errors look to code (below). Keep the description deterministic for a given catalog so client prompt caches stay warm.

**2. Outcomes a script can branch on.** Today a failed call rejects with a bare `Error` whose message is the only signal, so code (and the agent reading it) can confuse a denial with an unknown outcome; in benchmark run failure-and-denial #3 the agent reported a write that was DENIED twice as "unknown". Reject with an `Error` carrying a read-only `code` property (`DENIED`, `TOOL_ERROR`, `OUTCOME_UNKNOWN`, `CALL_TIMEOUT`, `INVALID_ARGUMENTS`, `RESULT_TOO_LARGE`, `DISPATCH_UNAVAILABLE`, `INVALID_RESULT`) plus `capability`, keeping the existing messages. For `DENIED` add `reason` (for example `WRITE_POLICY`). Nothing about the host, credentials or downstream internals may leak through these fields. Document the codes in the `execute` description.

**3. Benchmark checker.** Accept an answer whose entire text is one fenced code block (```` ```json ... ``` ```` or a bare fence) by parsing the fence's contents; anything else still has to be the exact JSON. Two runs in the phase 14 report were correct answers rejected only for the fence.

Tests: catalog rendering is deterministic, respects both bounds and falls back to namespaces; a catalog change regenerates the description and emits `list_changed`; a script can read `error.code` and `error.reason` for a denied write and distinguish it from `OUTCOME_UNKNOWN` and `TOOL_ERROR`; no error field contains a credential, path or downstream stack; the checker accepts fenced JSON and still rejects prose around it. Produce the phase handoff, including the new description text for a two-server example config.

**Test secrets (operator note, 2026-11-23):** buildctl refuses any changed file containing a credential-shaped literal (`ghp_…`, `sk-…`, JWT-shaped strings, or `token = "<long literal>"`-style assignments), even a fake one, and fails the phase. Build fake secrets at runtime instead, for example `FAKE_TOKEN = "ghp_" + "x" * 36`, and never write the assembled value into a source, fixture or snapshot file.
