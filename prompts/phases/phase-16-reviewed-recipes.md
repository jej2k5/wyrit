# Phase 16: Reviewed recipes

The phase 14 benchmark's best case, an agent handed a finished script for a 30-call fan-out, ran 4.3x cheaper and 3.3x faster than direct tool calls (2 model turns instead of 32), at full correctness. This phase makes that real: a **recipe** is a parameterized Wyrit script that an operator has reviewed and approved once, which agents can then run by name. Design principle 10 says to add runtime features only when evidence requires them; the benchmark is that evidence, and the scope here is deliberately narrow: no scheduling, chaining, replay or workflow engine.

**Recipe definition.** One file per recipe under a configured `recipes_path` directory (relative paths resolve against the config file), `<name>.json` holding: `name` (`[a-z][a-z0-9-]{0,63}`), `description`, `input_schema` (JSON Schema object for the arguments), `source` (the JavaScript, which receives its arguments as `args`), `capabilities` (each capability ID the source calls, with the SHA-256 digest of that capability's input schema and its read or write class at approval time), and `approval` (`approved_at`, `approved_by` as a free-text operator label, and `source_digest`, the SHA-256 of `source` plus `input_schema` plus `capabilities`). The file is the source of truth, as with `wyrit.toml`: hand edits and console edits are the same thing.

**Runnable only when approved and current.** A recipe is runnable only if its approval's `source_digest` matches its current content and every listed capability exists, is exposed, and still has the recorded schema digest and class. Otherwise it is listed as `pending`, `unapproved` (content changed after approval) or `stale` (name the capability that changed or disappeared) and cannot run. Re-check on load, reload and every capability refresh. A recipe never widens authority: the same sandbox, budgets and read/write policy apply to every call it makes, exactly as if the agent had sent the source to `execute`; a call to a capability not listed in the recipe fails with `INVALID_ARGUMENTS`-style rejection code `RECIPE_UNDECLARED`.

**Agent surface.** Add MCP tool `run_recipe(name, arguments)`: validate `arguments` against `input_schema`, run the recipe source with `args` bound, and return the same result shape as `execute`. Runnable recipes appear in the phase 15 `execute` catalog (under a "Recipes" heading: name, description, compact argument signature, and whether any listed capability is a write) and in `search` results. Add MCP tool `propose_recipe(name, description, input_schema, source)` so an agent can offer a script that worked; Wyrit derives `capabilities` by statically scanning `tools.call("<literal id>", …)` calls (reject proposals that call capabilities through non-literal IDs), validates everything, and writes it as `pending` with no approval. A proposal can never approve itself or overwrite an approved recipe; proposing an existing name creates `<name>` as pending only if no file exists, otherwise it is refused with the reason.

**Console.** A Recipes page in the phase 12/13 console, same design system and security rules (loopback, per-launch token on every change, CSP, no external resources). It lists recipes by state; shows a recipe's source (monospace, preserving whitespace), argument schema, the capabilities it calls with read/write class, and, for an unapproved recipe, a diff against the last approved content when the console has one; offers Approve (records `approval` with the operator label entered on the page), Revoke (removes approval) and Delete (with a confirm step). Approval writes the file atomically with a backup and applies live through the phase 9 reload. Per-recipe run stats come from the ledger (runs, success rate, p50/p95 duration), which records `recipe` name and `source_digest` on every recipe run.

Tests: an approved recipe runs through `run_recipe` with validated arguments; a content edit makes it unapproved; a capability schema or class change makes it stale with the capability named; an undeclared capability call is rejected; write policy and budgets apply inside recipes; `propose_recipe` writes a pending file and cannot approve or overwrite; the catalog and `search` list only runnable recipes; console approve/revoke/delete round-trip through the file and require the token; the ledger carries recipe name and digest. Produce the phase handoff with one worked example recipe (the phase 14 fan-out: list tickets, fetch each, count and sum).

**Test secrets (operator note, 2026-11-23):** buildctl refuses any changed file containing a credential-shaped literal (`ghp_…`, `sk-…`, JWT-shaped strings, or `token = "<long literal>"`-style assignments), even a fake one, and fails the phase. Build fake secrets at runtime instead, for example `FAKE_TOKEN = "ghp_" + "x" * 36`, and never write the assembled value into a source, fixture or snapshot file.
